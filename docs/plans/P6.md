# P6: many elections and many sources in one lake

Goal: the lake holds more than the 2026 urna logs. Each source writes Parquet tables that join
on two shared keys: the municipality (`id_municipio`, with its TSE and SIAFI codes) and, for
people, `id_pessoa`. TSE results for 2018, 2022 and 2024 load next to 2026. P7 and P8 do not wait for this plan;
P9 needs `id_pessoa`.

Why now: every source found in the research of 2026-10-31 joins through a municipality code,
but each uses a different one (IBGE 7 digits, TSE 5 digits, SIAFI 4 digits), and TSE's candidate
id (`SQ_CANDIDATO`) changes every election. Without the shared keys, each new source would
bring its own join.

## Facts this plan builds on (checked 2026-11-01)

- F1 `br_bd_diretorios_brasil.municipio` maps TSE to IBGE codes from TSE's own file
  (`municipio_tse_ibge.csv`, generated 2026-10-25). Blumenau 80470 / 4202404, Três Cachoeiras
  85367 / 4321667.
- F2 The Portal da Transparência benefit files key the city by SIAFI code (Blumenau 8047,
  Três Cachoeiras 7329) plus name and UF. The Portal API keys it by IBGE code.
- F3 `config.ELECTIONS` holds only 2026, with a results-site `id_pleito`. Older elections are
  on CKAN only (`dadosabertos.tse.jus.br`), as yearly CSV zips, latin-1, `;`.
- F4 TSE voting places 2026 (`eleitorado_local_votacao_2026.zip`, 167 MB): latitude and
  longitude for every place in both pilot cities. A place is (`NR_ZONA`, `NR_LOCAL_VOTACAO`):
  the place number repeats across zonas (Blumenau: 52 numbers, 60 places).
- F5 TSE candidate files carry `NR_TITULO_ELEITORAL_CANDIDATO` in every year; candidate CPF is
  masked in 2024. The voter-registration number agrees with CPF on 3,796 of 3,796 shared
  values 2014 to 2022 (research note a8, not re-run).

Rules the diagram encodes:
- R1 One module per publisher, each with `fetch` (download or API, with a rate limiter and
  resume) and `read_*` (file to `pyarrow.Table` with exactly the catalog columns).
- R2 Every table with a place carries `id_municipio` (IBGE, 7 digits). Sources keyed by TSE or
  SIAFI code are translated on load through `ref.municipio`, and a code that does not
  translate fails the load.
- R3 Every table about a person carries `id_pessoa` (P9). Names, CPF, NIS and voter numbers of
  private persons never enter a public table; `br_bd_diretorios_brasil.pessoa` stays private.
- R4 Each table is partitioned by `ano` (and `mes` for monthly sources), so a new year or month
  is a new partition and a rerun replaces only that partition.
- R5 Raw downloads stay in `raw/<publisher>/` with their checksum; the lake can be rebuilt
  from raw without the network.

## Decisions (2026-11-01)

- D1 Municipality key is IBGE `id_municipio`; `id_municipio_tse` stays on TSE tables as well.
- D2 `ref.municipio` gains `id_municipio_siafi`. Source: the official SIAFI to IBGE table if
  one is found (T2 looks for it); otherwise derived by matching (UF, normalized name) between
  a Portal file and `municipio`, and the load fails unless every SIAFI code in the Portal file
  matches exactly one IBGE code.
- D3 `id_pessoa` = SHA-256 of (`BRASILDB_PESSOA_SALT`, voter-registration number). The salt
  is a secret and lives outside the repo.
- D4 Older elections come from CKAN only; `Election.id_pleito` becomes optional.
- D5 Dataset names follow Base dos Dados where a matching dataset exists; where not checked,
  the name in this plan is provisional and T1 confirms it.

## Contracts

- `catalog.yaml`: new columns and tables before code.
- `brasildb/ref/municipio.py`: `read_municipio(tse_csv, siafi_source) -> pa.Table` with
  `id_municipio, id_municipio_tse, id_municipio_siafi, sigla_uf, nome`.
- `brasildb/ref/keys.py`: `to_ibge(table, column, kind)` where kind is `tse | siafi`; raises
  on any code with no match.
- `brasildb/config.py`: `ELECTIONS` gains 2018 (1, 2), 2022 (1, 2), 2024 (1, 2).
